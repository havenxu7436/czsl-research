# 导师代码可修改性与后续实验落地评估

## 1. 结论

**可以在这两份代码的基础上继续做实验设计中的方案，但不能把当前压缩包直接视为“已跑通、可直接合并”的两个基线。**

推荐的工程路线是：

1. 以 `CRMask_copy` 为主线，先重建并验证一个可信的 CPF baseline；
2. 不整体合并 `LogiCZSL_copy`，而是从中抽取 Troika/CLIP 部件、知识表示思路和逻辑损失公式；
3. 重新定义统一的知识文件格式与模型接口；
4. 按 A–H 变体逐层加入 Text K、`K_oa`、Feature K 和 Logic loss。

因此，这项任务属于“**可落地，但需要先修复基线和重构接口**”，不是“改几个超参数即可开始主实验”。只要缺失的知识文件可以从导师处拿到或按明确规则重新生成，实验设计中的 A–H 均可以实现。

## 3. CPF 代码的真实状态

### 3.1 可以复用的部分

- 数据集读取与属性/物体/组合标签组织；
- ViT 视觉骨干及多层特征抽取框架；
- GloVe primitive embedding 加载；
- object、attribute 与 composition 分支的主体结构；
- 配置系统、训练循环和优化器框架。

这些内容足以作为新实现的工程骨架，不需要推倒重写。

### 3.2 必须先解决的问题

| 问题 | 代码证据 | 影响 | 处理方式 |
|---|---|---|---|
| 实验设计把 `models/ddm_v3.py` 写成 CPF 核心，但训练入口实际导入 `models.ddm_v2.DDM` | `train.py:12`、`test.py:7` | 设计文档与真实运行模型不一致 | 新建唯一、明确的 `models/cpf.py`，禁止继续靠 `ddm_v1/v2/v3/v4` 猜版本 |
| 训练依赖的 `evaluator_ge.py` 不在压缩包中 | `train.py:14` | 训练一开始就会导入失败 | 根据已有 evaluator 与论文指标补齐统一 evaluator |
| 测试依赖的 `dataset_visualization.py`、`evaluator_ge_v.py` 缺失 | `test.py:8-9` | 原测试脚本不可运行 | 改成共用 dataset/evaluator，不保留仅作者环境可用的入口 |
| `image_soft_weights()` 把 query 和 key 覆盖为全 1 | `models/ddm_utils.py:15-16` | 注意力退化为近似均匀权重，语义引导失效 | 移除调试代码，并加注意力非均匀性单元测试 |
| 当前 `ddm_v2` 的部分 TEO/OGA 路径被注释 | 模型的 train/val 分支中存在成组注释 | 运行结果不等于论文完整 CPF | 依据论文公式重建 TEO/OGA，并对中间张量做 shape 与数值测试 |
| 配置与论文/复现实验不完全一致 | MIT seed 为 `-1`，部分学习率里程碑晚于总 epoch | 结果难以复现和公平比较 | 固定 seed、epoch、LR schedule，并把最终配置随 checkpoint 保存 |

### 3.3 CPF 的可修改性判断

CPF 适合作为后续工作的**主代码库**，但第一版实验 A 必须使用“修复并冻结后的 CPF”，不能直接把现有 `ddm_v2` 输出称为论文 CPF baseline。否则后续 E/H 即使提升，也无法判断提升来自知识模块还是来自对 baseline bug 的修复。

## 4. LogiCZSL 代码的真实状态

### 4.1 可以复用的部分

- Troika 的 CLIP 图像/文本编码框架；
- adapter、disentangler、cross-attention 等模块；
- HC、ODA、ADA 三类约束的逻辑损失公式；
- feasibility 数据和常规 CZSL 评估代码的部分实现；
- 用 primitive 与扩展概念构造附加分支的总体思路。

### 4.3 LogiCZSL 的可修改性判断

`LogiCZSL_copy` 更像作者实验目录的中间快照，而不是发布版仓库。它适合做“**算法参考与部件来源**”，不适合作为完整应用直接并入 CPF。要独立复现 LogiCZSL，还需要：

1. 获取或重建每个数据集的 OI/HC、OE/ODA、AE/ADA 知识文件和 compatibility matrix；
2. 统一概念命名、字段名和映射方向；
3. 修复训练、模型工厂、逻辑模型和测试之间的接口；
4. 重写逻辑 prompt/visual feature 的数量与 shape 设计；
5. 再验证论文指标。

## 5. 实验设计中需要修正的实现假设

实验设计的研究方向总体合理，但下面几处不能原样照抄。

### 5.1 `ddm_v3.py` 不是当前训练入口

文档把 `ddm_v3.py` 标为 CPF 核心，真实 `train.py/test.py` 使用的是 `ddm_v2.py`。在实现知识模块前，必须先确定一个经过验证的 CPF canonical model。

### 5.2 `logic_copy.py` 不是可直接调用的“完整模型”

它与数据集字段、工厂函数、prompt 数量、视觉特征数量和测试入口均不闭合。逻辑损失需要抽取、清理和重写接口，不能直接 `import` 后挂到 CPF。

### 5.3 Text K 与原 CPF 的 GloVe 空间不天然兼容

原 CPF 使用 GloVe primitive embedding；设计文档中的 object description、attribute description 和 pair sentence 更接近 CLIP/句子编码器输入。两种可比方案是：

- **保守版**：继续在 GloVe 空间，用词元平均或可复现的短语聚合构造 `W_o^K/W_a^K`；
- **增强版**：引入冻结文本编码器，但必须把“更强文本编码器”单独做消融，否则收益不能归因于知识。

第一轮 A–F 推荐先做保守版；增强版作为额外实验。

### 5.4 Feature K 的张量假设需要重写

设计文档假设 `v_obj` 为 `B×N×D`、`v_attr` 为 `B×M×D`，而原 CPF 的主体并不天然产生这两个张量。应先明确：

- object logits：`B×N`；
- conditional attribute logits：`B×N×M`，按 object chunk 计算；
- pair score：`z_obj[:,:,None] + z_attr_obj + lambda_k*K_prior`。

不建议为了满足伪代码，直接复制视觉特征生成巨大的 `B×N×D`/`B×M×D` 张量。

### 5.5 `W_ao^K` 不能无条件完整常驻显存

以 CGQA 的 674 个 object、413 个 attribute 为例，完整 `N×M×D`：

- `D=300`、FP32 约 319 MiB；
- `D=768`、FP32 约 816 MiB；
- `D=1024`、FP32 约 1.06 GiB。

这还未包括梯度、优化器状态和中间激活。推荐使用 factorized 表示、磁盘分块或按 object chunk 动态编码，不把完整张量设为可训练参数。

### 5.6 `K_oa` 的使用需要同时比较 hard 与 soft object conditioning

设计中的“先检测 object，再取一行 `K_oa[o_detected]`”会把 object argmax 错误直接传播给 attribute。建议同时实现：

- hard：`K_oa[argmax P(o|x)]`；
- soft（主版本）：`P(o|x) @ K_oa`。

soft 版本可微、对 object 不确定性更稳，适合成为新方法的一部分。

### 5.7 知识来源必须做泄漏审计

所有 description、compatibility、LLM feasibility 只能依赖 primitive 名称和外部通用知识，不能读取 val/test pair 标签或其频率。必须保存生成 prompt、来源、模型版本、随机种子和覆盖率报告。

## 6. A–H 方案的实际可实施性

| 变体 | 可实施性 | 前置条件 | 主要工作量/风险 |
|---|---|---|---|
| A. CPF-only | 可实施 | 修复 evaluator、CPF 主模型与配置 | 中；是所有实验的度量基准 |
| B. CPF + external logic | 可实施 | 重建知识图与统一 mapping | 中高；不能直接复用原 `LogicLoss` 接口 |
| C. CPF + richer text | 可实施 | 确定 GloVe 或冻结文本编码器方案 | 中；需隔离 text encoder 增益 |
| D. CPF + calibration | 最容易实施 | 生成合法的 `K_oa` | 低到中；建议最先做 |
| E. Text + calibration | 可实施 | C、D 单独验证通过 | 中 |
| F. MVP + logic | 可实施 | B、E 训练稳定 | 中高；需要 beta warm-up/调参 |
| G. Feature K | 可实施 | canonical shape API、chunk scoring | 高；属于真正的新模块 |
| H. Full model | 可实施 | G 稳定并完成消融 | 高；需完整 A–H 与 sanity checks |

推荐推进顺序不是直接做 H，而是：`A → D → C → E → B → F → G → H`。这样能最快发现 `K_oa` 是否有价值，也能避免逻辑损失和新特征头同时出错时无法定位原因。

## 7. 推荐代码结构

建议新建干净工作副本，保留原压缩包只读，并采用下面的结构：

```text
project/
├── models/
│   ├── cpf.py                 # 唯一 canonical CPF
│   ├── knowledge_text.py      # Text K
│   ├── conditional_head.py    # B×N×M / chunk scoring
│   └── logic_adapter.py       # 重写后的 HC/ODA/ADA 适配器
├── knowledge/
│   ├── schema.py              # 统一命名和索引
│   ├── build_embeddings.py
│   ├── build_compatibility.py
│   └── validate_assets.py
├── evaluation/
│   └── evaluator.py
├── configs/
│   ├── cpf_baseline.yaml
│   └── variants/{A,B,C,D,E,F,G,H}.yaml
├── tests/
│   ├── test_shapes.py
│   ├── test_logic_loss.py
│   ├── test_no_leakage.py
│   └── test_attention.py
└── scripts/
    ├── train.sh
    ├── eval.sh
    └── run_ablation.sh
```

所有变体共用同一训练/评估入口，只通过配置开关控制：

```yaml
knowledge:
  text_k: false
  compatibility_k: false
  feature_k: false
  logic_loss: false
```

这样才能保证 A–H 的 backbone、数据、优化器、seed 和 evaluator 完全一致。

## 8. 我可以直接代为完成到什么程度

在有代码目录和服务器运行反馈的情况下，可以完成：

1. 建立不覆盖原文件的 Git 工作副本；
2. 修复 CPF 训练、验证、测试与 checkpoint，建立 A 基线；
3. 修复或重建 LogiCZSL 的知识 schema 和逻辑损失单元测试；
4. 编写知识预处理、覆盖率、shape、NaN、泄漏检查；
5. 实现 A–F MVP，包括 Text K、hard/soft `K_oa`、logic warm-up；
6. 实现 G/H 的 factorized 或 chunk-wise Feature K；
7. 写三数据集、多 seed 的批量训练/评估命令；
8. 自动汇总 Seen、Unseen、HM、AUC、参数量、速度与显存；
9. 根据服务器日志继续定位 CUDA OOM、维度、数据映射和指标问题；
10. 最终输出可复现实验表、消融表和代码修改说明。

不能凭现有压缩包保证的事项：

- 在缺失作者 knowledge JSON/CSV 时精确还原 LogiCZSL 论文数值；
- 在 CPF 官方实现细节缺失时保证逐位复现作者数值；
- 在没有目标服务器/GPU 执行结果时宣称端到端训练已经通过；
- 用未经审计的 LLM 知识直接宣称无测试集泄漏。

## 9. 现在最合适的下一步

先不要修改唯一的服务器代码目录。创建一个工作分支/副本，第一阶段只做下面四件事：

1. 固定一个数据集（推荐 UT-Zappos）和一个 seed；
2. 修复 CPF canonical baseline，并记录 A 的 val/test 指标；
3. 生成并校验 `K_oa`，先跑 D；
4. 在 A、D 均稳定后再加入 Text K，形成 C/E。

**是否进入后续创新的判据**：A 能稳定复现；D 或 E 相对 A 的 HM/AUC 有稳定收益；同一配置重复运行无 NaN、无映射错位、无知识泄漏。达到这一点后，再接逻辑损失和 Feature K 才有研究意义。
